# FAQ: кэширование в SummerSchoolProject

Вопросы и ответы, возникшие при разборе коммитов 2–3 (кэш ленты/картинок и инвалидация кэша).

---

## 1. Почему в коммите 3 (cache invalidation) из `ImageLoader` убрали `URLCache`? Разве не нужно было сразу использовать только `NSCache`?

**Причина удаления — конкретный баг, а не рефакторинг.** CDN `picsum.photos` отдаёт картинку через **302-редирект** на `fastly.picsum.photos/...`. `URLSession` следует редиректу прозрачно, но `URLCache` сохраняет ответ под ключом **финального** URL, а поиск (`cachedResponse(for:)`) идёт по **исходному** → систематический cache miss. Дисковый слой для картинок фактически никогда не срабатывал.

**Почему именно в коммите 3:** тема коммита — управляемая инвалидация (TTL, версия схемы, очистка при логауте). Управлять кэшем, который ключуется неизвестными приложению CDN-URL, невозможно: нельзя адресно удалить записи и нельзя построить TTL. Поэтому отключение `URLCache` в [`ImageLoader.swift`](SummerSchoolProject/Networking/ImageLoader.swift) (`config.urlCache = nil`, `.reloadIgnoringLocalCacheData`) едет вместе с появлением `CacheManager`.

**«Только `NSCache`» никогда не было бы достаточно:** это чисто in-memory кэш — умирает при перезапуске и вычищается ОС под memory pressure. Офлайн после перезапуска без дискового слоя не работает вовсе. Правильная формула — та, что и получилась: **`NSCache` (L1, RAM) + свой файловый кэш с ключом `SHA256(исходный URL)` (L2, диск) + сеть (L3)**. Так же устроены Kingfisher/SDWebImage/Nuke.

## 2. Почему на сборке коммита 2 картинки видны после pull-to-refresh при полностью выключенной сети? Ожидался промах

Промах ожидался от **дискового** слоя (`URLCache`), но pull-to-refresh до него не доходит:

1. **`NSCache` в RAM жив.** Pull-to-refresh не перезапускает процесс. Картинки лежат в памяти под исходным URL (кладём сами в `store(_:for:)`), и `image(for:)` возвращает хит до любого обращения к сети/`URLCache`.
2. **SwiftUI view identity.** В `CachedAsyncImage` стоит `.task(id: url)` — таск перезапускается только при смене URL. Refresh возвращает те же посты с теми же URL → `@State var image` сохраняется, `load()` вообще не вызывается.

**Как воспроизвести настоящий промах:** загрузить ленту онлайн → **убить приложение** (RAM-кэш умер) → выключить сеть → запустить. JSON ленты придёт из `URLCache` `api-cache` (там редиректа нет), а картинки уйдут в `catch`, где `cachedResponse(for:)` промахнётся из-за редиректного ключа → плейсхолдер `wifi.slash`.

Нюансы эксперимента: сеть на симуляторе надёжнее рубить через Network Link Conditioner или Airplane Mode на устройстве; у `ImageLoader` коммита 2 нет таймаута — падение запроса может занять десятки секунд.

## 3. `NSCache` — это только про RAM?

**Да, исключительно in-memory.** На диск не пишет никогда.

- Живёт только пока жив процесс: kill из app switcher / выгрузка системой → кэш пуст.
- Не переживает memory pressure: ОС сама вытесняет записи (`countLimit`/`totalCostLimit` + автоэвикция) — это фича, защита от OOM.
- Потокобезопасен из коробки, в отличие от `Dictionary`.
- Ключи должны быть классами и не копируются — отсюда `NSURL` и касты `url as NSURL`.

Поэтому в трёхуровневой схеме `NSCache` покрывает только «горячий» скролл в рамках сессии; перезапуск и офлайн — задача дискового слоя.

## 4. Как тогда работает `URLCache`? Почему посты видны после перезапуска — разве он не хранит их в RAM?

`URLCache` — **двухуровневый**: RAM + диск. В `APIClient.init()` задаются `memoryCapacity: 16 MB` (оперативка, живёт с процессом) и `diskCapacity: 128 MB`, `diskPath: "api-cache"` (SQLite + файлы в `Library/Caches`, переживают перезапуск).

Поиск идёт каскадом: RAM → диск → сеть. После перезапуска RAM пуст, но запись находится на диске.

Посты попадают на диск и находятся, потому что:
1. JSONPlaceholder отвечает `200` c `Cache-Control: max-age=43200` и `ETag` — сервер разрешил кэшировать;
2. редиректа нет — ключ сохранения совпадает с ключом поиска (в отличие от картинок);
3. офлайн срабатывает ручной фолбэк `cache.cachedResponse(for:)` в `APIClient.get(_:)`, который читает запись с диска даже протухшую по HTTP.

Оговорка: `Library/Caches` ОС вправе вычистить — `URLCache` не источник правды, критичные данные (билет) живут в `Application Support`.

## 5. Почему `URLCache` пишет именно на диск, а не в RAM?

Посылка неточная: он пишет **в оба уровня**, диск — основной, RAM — горячий индекс поверх. Куда попадёт конкретная запись, решают:

- **Ёмкости:** эвристика Foundation — ответ кэшируется в слой, только если занимает не более ~5% его ёмкости. Мелкий JSON → RAM + диск; крупный ответ → только диск.
- **`CachedURLResponse.storagePolicy`:** `.allowed` (RAM+диск), `.allowedInMemoryOnly` (только RAM), `.notAllowed`.
- **Заголовки сервера:** `no-store` → никуда; `no-cache` → хранить, но ревалидировать; `max-age`/`ETag` → полноценное хранение.
- `diskPath: nil` / нулевая `diskCapacity` → чисто RAM-кэш.

Важно: это эвристики закрытой реализации, Apple документирует лишь «composite in-memory and on-disk cache» — без контракта, что и когда окажется на диске.

## 6. Мы как-то очищаем `URLCache`?

**Да, целиком** — `urlCache.removeAllCachedResponses()` внутри `CacheManager.clearAll()` ([`CacheManager.swift`](SummerSchoolProject/Cache/CacheManager.swift)). Два триггера:

1. **Логаут:** `SessionStore.logout()` → `clearAll()` — чистит HTTP-ответы, TTL-метки в `UserDefaults` и картинки через `ImageLoader.clearCache()` (единая точка очистки).
2. **Смена версии схемы:** `validateSchemaVersion()` в `init` при несовпадении `cacheSchemaVersion` вызывает тот же `clearAll()`.

Нюансы:
- Точечной инвалидации нет: TTL реализован метками времени поверх кэша (протухшее помечается `.staleCache`, но физически не удаляется) — паттерн stale-while-revalidate.
- Чистится только инстанс, которым владеет `CacheManager`; осиротевший `image-cache` от сборки коммита 2 никем не удаляется.
- `removeAllCachedResponses()` работает с диском асинхронно, без гарантии момента завершения.

## 7. Почему очистка `URLCache` при логауте «ненадёжна»?

Надо разделить два сценария:

**А. Полный снос (`removeAllCachedResponses()`)** — аргумент «неизвестные CDN-URL» тут не применим (ключи не нужны). Реальные проблемы:
1. **Нет гарантии момента завершения:** метод возвращается сразу, работа с SQLite идёт на внутренней очереди, completion-хендлера нет.
2. **Гонка с запросами в полёте:** запрос пользователя A, завершившийся после очистки, запишет его данные в уже «чистый» кэш (таймаут 5 с — окно реальное; отмены летящих задач при логауте в проекте нет).
3. **Чистится только свой инстанс:** другие инстансы (`URLCache.shared`, осиротевший `image-cache`) остаются нетронутыми.
4. **Исторический багаж:** в старых iOS были баги неполной очистки диска; проверить результат нечем — API чтения содержимого кэша нет.

**Б. Адресная инвалидация (`removeCachedResponse(for:)`)** — здесь редиректы бьют по-настоящему: записи картинок лежат под `fastly.picsum.photos/...`, которых приложение никогда не видело. Удалить адресно невозможно в принципе.

**Контраст со своим кэшем:** `ImageLoader.clearCache()` — синхронный `FileManager.removeItem(at:)`: вызов вернулся → папки нет (контракт файловой системы). Ключи детерминированы (`SHA256`), всё в одном известном месте.

**Честная оценка:** «ненадёжно» ≠ «не работает». Свой кэш даёт **проверяемые синхронные гарантии**, `URLCache` — **асинхронное best-effort без обратной связи**. Для барьера безопасности между пользователями эта разница принципиальна.
